## Dependency direction

Platform modules depend on the shared entity base, runtime data, coordinator
snapshots, and constants. The lifecycle module constructs the runtime and
coordinators and forwards platforms. Only `config_flow.py` and `coordinator.py`
construct `wab11.WAB11Client` instances; only the coordinator/runtime module
uses library models for live entity data and write operations. Tests enter
through Home Assistant config flows, config-entry lifecycle, entity services,
custom services, or diagnostics rather than replacing integration source
objects.

The manifest pins the production library version. `requirements_test.txt`
installs the same pinned library plus the Home Assistant custom-component test
plugin. `requirements_dev.txt` extends that environment with Home Assistant,
Ruff, mypy, and flake8. The exact automated commands and release triggers are
kept in the
[`validation and release workflow`](workflows/validation-release.md).

The base library owns the meaning of omitted versus explicit circuit counts,
including its structured Modbus exception boundary. That upstream contract is
recorded in
[`wab11/.docs/contracts/heating-circuit-discovery.md`](../../../.docs/contracts/heating-circuit-discovery.md).
For a new entry, this integration performs detection only during validation;
the detected or manual integer then flows through config-entry data, an
optional options override, lifecycle setup, `Wab11Runtime`, and finally the
library constructor. An older entry without the data field retains the
library's `None` auto-detection behavior until the editable option is saved.

The entity descriptions deliberately stop at the synchronized runtime
boundary. `HeatingCircuit.status`, `HotWaterState.status`, and the
`InputsState.config_*` fields exist in the library model but are not populated
by current full synchronization, so they are not exposed as entities. The
complete register-to-model-to-Home-Assistant matrix is kept in the root
[`variables reference`](../../../docs/variables-reference.md).
